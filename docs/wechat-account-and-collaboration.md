# 微信小程序账号体系与团队协作说明

> 「衣适」黑客松项目配套文档 · 记录账号、AppID、云环境三者的关系与团队协作方式

---

## 一、三层结构：账号 → AppID → 环境 ID

一句话概括：**账号是「谁」，AppID 是「这个谁的编号」，环境 ID 是「这个编号下的某间办公室」。**

```
微信小程序账号（公司主体注册，云端唯一）
├── AppID（账号的唯一编号，相当于身份证号）
│     └── 云开发环境 ID（云资源的门牌号，可开多个：dev / prod）
└── 成员管理（把员工的微信号授权进来，赋予不同角色）

本地项目（开发者工具里的代码，本身不属于任何账号）
      ↑ 填上 AppID，就"绑定"到这个账号
```

| 概念 | 是什么 | 决定了什么 | 在哪里改 |
|---|---|---|---|
| **小程序账号（主体）** | 法律上的归属，公司注册获得 | 谁有权发布、谁承担备案责任、能不能用支付 | mp.weixin.qq.com 后台 |
| **AppID** | 账号的唯一编号，终身不变 | 工具登录哪个账号、云资源归属、后端接口识别来源 | `project.config.json` |
| **环境 ID** | 云资源的门牌号（数据库、存储、云函数都在里面） | 代码连哪套云资源 | `utils/config.js`（`wx.cloud.init({ env })`） |

### 关键性质

- **一个账号 = 一个 AppID**，AppID 不能换绑到另一个账号
- **一个 AppID 下可开多个环境**：`dev` 开发用、`prod` 正式用，数据库完全隔离
- **同一 AppID 可被无数个本地项目副本使用**：队友各自拉一份代码填同一个 AppID 即可

## 三、成员角色与权限（企业如何"分配"开发权）

**企业不会给员工分配一个小程序账号，而是把企业已有的账号授权给员工的微信号。**

一个 AppID 永远只有一个，属于企业；员工用的是自己的微信号作为登录身份。

### 3.1 权限是"可勾选的组合"，不是单一角色

添加成员时可以分别勾选下面这些权限，按需给：

| 权限 | 能做什么 | 什么时候要给 |
|---|---|---|
| **开发者** | 用微信开发者工具打开该项目、上传代码、预览、真机调试、用云开发（云函数/数据库/存储） | **要让队友写代码，必须给这个** |
| **体验者** | 扫码使用「体验版」小程序（只能看，不能改代码） | 给评审/老师/家人试用。**这是独立的勾选项，可以叠加在「开发者」上** |
| **开发管理** | 提交审核、发布、回退版本 | **一般不给**，避免误发布 |
| **开发设置** | 配置服务器域名、消息推送、扫普通链接打开小程序 | 一般不给 |
| **数据分析** | 查看小程序后台数据 | 只做运营的人 |
| **登录** | 无需管理员确认即可登录 mp 后台 | 需要看后台的人 |
| **暂停服务设置** | 暂停线上服务 | 不给 |

> ⚠️ **只给「开发者」，不给「开发管理」**，是这个项目推荐的组合——队友能开发、能调试、能部署云函数，但无法把小程序发布上线。

### 3.2 「开发者」能体验到什么程度？

**能，而且够用。** 权限是勾选项不是角色，所以「开发者」本身就能看到小程序跑在真机上的样子，不需要额外做什么。

| 想做的事 | 开发者能不能 | 怎么做 |
|---|---|---|
| 在电脑上看效果 | ✅ | 开发者工具里直接编译，模拟器就是效果 |
| 在自己手机上看 | ✅ | 工具点「预览」→ 手机扫二维码 → 打开的是**开发版** |
| 真机调试、看报错日志 | ✅ | 工具点「真机调试」 |
| 用「体验版」（独立入口、可发给别人扫） | ✅ | 前提是这个微信号**也被勾了「体验者」**，或本身就是项目成员 |
| 上传代码 | ✅ | 工具点「上传」 |
| 提交审核 | ✅ | 需要「开发管理」权限 |
| **发布上线** | ❌ | 只有管理员能发布 |

四种版本的关系，一张表讲清楚：

| 版本 | 谁看得到 | 怎么产生 |
|---|---|---|
| **开发版** | 只有上传它的那个人 | 开发者工具点「上传」 |
| **体验版** | 所有被勾了「体验者」的人 + 项目成员 | 管理员在后台把某个开发版「设为体验版」 |
| **审核中版本** | 微信审核员 | 从体验版提交审核 |
| **线上版** | 所有人 | 审核通过后管理员发布 |

> 关键点：**开发版是"每人一份"，体验版是"全项目一份"。** 队友上传的开发版只有他自己扫得到；要让全队或评审看到同一个版本，得由管理员设一个体验版。

**还有一个省事的点**：项目成员（包括只有「开发者」权限的人）**自己就能添加、删除体验成员**，不必找管理员。演示前如果老师或同学要试用，Nancy 用自己那个微信号在 mp 后台「成员管理」里直接加就行。当然，这个便利也意味着成员权限要选可靠的人——他们能往项目里加人。

### 3.3 人数上限

有两个方向的上限，别混：**小程序账号这一侧能装多少人**，和**微信号这一侧能挂多少个小程序**。

**方向一：每个小程序账号能加多少项目成员**（不区分权限组合）

| 账号类型 | 上限 |
|---|---|
| 个人主体 | 15 |
| 组织主体 · 未认证未发布（**本项目当前属于这一档**） | 30 |
| 组织主体 · 已认证未发布 / 未认证已发布 | 60 |
| 组织主体 · 已认证已发布 | 90 |

**方向二：一个微信号最多能挂多少个小程序**

| 身份 | 一个微信号的上限 |
|---|---|
| **管理员** | **5 个小程序**（每个小程序只有 1 名管理员） |
| **开发者 / 项目成员** | **50 个小程序** |

> ⚠️ 这两个额度是**按微信号算的，跨主体累加**。你管的这 5 个小程序里，不管是自己的、公司的、还是帮朋友挂的，**都占同一个 5 的额度**。所以「反正不同 owner，应该不占额度」是错的。
>
> 额度不够时的解法：让**另一个人**当第 6 个的管理员（比如让队友当）。换管理员需要**原管理员扫码授权**，所以那个人得还在、还得肯配合——这就是为什么每个小程序的**管理员微信号必须是长期可控的人**。
>
> 顺带一提：小程序和公众号的额度**互不占用**（官方原话：「管理员及其他项目成员绑定账号数不占用公众号绑定数量限制」）。

### 3.4 添加步骤（管理员操作）

1. 用**管理员微信号**登录 mp.weixin.qq.com
2. 左侧进「管理 → 成员管理」（部分版本显示为「用户身份 → 开发者」）
3. 点「绑定开发者」/「添加成员」
4. 输入对方的**微信号**——不是昵称、不是手机号。对方如果从没设置过微信号，需要先让他去设置
5. 勾选权限：**只勾「开发者」**
6. 提交

**关键：现在不需要对方确认。** 早年的流程是「发邀请 → 对方点确认」，现在管理员直接输入微信号点添加就绑定成功了。

> 反过来说这也有个副作用：被添加的人在完全不知情的情况下就成了某项目的成员。定期去 mp 后台「成员管理」或微信「公众平台安全助手」核对自己的绑定列表，是个好习惯。

### 3.5 队友拿到权限后要做的三件事

1. 下载微信开发者工具，**用自己被添加的那个微信号**扫码登录
2. 从 Git / 压缩包拿到 `yishi` 代码（**加权限只给云端身份，不给她代码**）
3. 导入项目，AppID 保持 `wx5b899ef4f7bef91e` 不变，然后就能编译、预览、上传

> 自己手机上看效果最快的一条路：工具点「预览」→ 二维码发到自己微信 → 手机扫码。**预览二维码有时效**，过期了重新点一次「预览」生成新的就行。这条路不需要任何后台设置，是黑客松期间最常用的验证方式。

**删人**：从「成员管理」移除，立刻失效。代码和云端资源都还在企业账号下，一样不少。

### 3.6 成员属于「小程序账号」，不属于「公司」

**一句话：开发者身份的本质是「微信号 × AppID」的一条绑定记录，存在那个小程序账号里。**

「主体」（公司）这一层**没有一份成员名单**。主体决定的是「这几个 AppID 归谁所有」，不决定「谁能开发」。这两件事在微信里是分开的。

推出来的三条：

1. **公司名下有三个小程序，就要设置三遍。** 没有「公司级开发者」这种东西，也没有能一次生效的地方。
2. **「离职」在微信后台不存在，只有「移除成员」这个动作。** 人走了，只要没人去删，他仍然是这三个小程序的开发者——而且要删三遍。
3. **同一个微信号可以同时是任意多家主体的开发者**，这些绑定互不影响，只受 5 个管理员 / 50 个开发者 的额度约束。

**微信开发者平台合并了入口，但没有合并添加动作**

`developers.weixin.qq.com` 是新的「一站式工作台」，把你有权限的小程序、小游戏、公众号、服务号、微信小店、移动应用、网站应用、开放平台都汇总在一个界面里，不用记一堆后台地址、不用来回切登录。

> ⚠️ **「无需切换多个后台」≠「一次添加三处生效」。** 添加成员这个动作仍然落在某一个具体账号下。它省的是切后台的麻烦，**不是添加的次数**。

**三层权限，别混**

| 在哪一层 | 管什么 | 粒度 | 在哪设 |
|---|---|---|---|
| **小程序账号层** | 谁能以这个 AppID 开发 | **一个 AppID 一份名单** | mp 后台「用户身份 / 管理 → 成员管理」，或开发者平台的成员管理 |
| **云开发权限层** | 这个开发者能碰哪些环境、哪些资源 | 一个小程序内可勾多位开发者「批量设置」，可勾「全部环境应用」 | 云开发控制台 → 权限设置 |
| **开放平台层** | 用户身份的 UnionID 打通 | 和成员权限**完全无关** | 开放平台 |

> 第二层的「批量设置」容易误会成"能跨小程序批量"——**不能**。它只是在一个小程序自己的开发者之间批量勾选，作用范围还是那一个小程序。
>
> 第三层也常被误解：把几个小程序绑到同一个开放平台账号，能打通**用户身份**（UnionID），但**不会**让成员权限合并。这两件事没有任何关系。

**实践建议：因为微信没有公司级名单，你必须自己在微信之外维护一张。**

一张「谁在哪些小程序里」的矩阵表（姓名 × 小程序），放进代码仓库。原因是漏加和漏删**都不会有任何提示**：

- 漏加的症候是「能打开项目，但预览/上传报无权限」——他要自己撞上才知道
- 漏删的后果是离职的人**仍然能上传代码**——你不主动查就永远不知道

## 四、四种典型的"分配"场景

### ① 企业内部团队协作（本项目场景）

1. 管理员在「成员管理」把每位队友加为「开发者」
2. 队友从 Git 拉 `yishi` 代码，`project.config.json` 保持同一个 AppID
3. 队友用自己的微信扫码登录开发者工具

> ⚠️ **云函数部署是"谁上传谁生效"**，多人同时改同一个云函数容易互相覆盖。黑客松期间约定：**云函数只由一个人负责部署**。

### ② 外包 / 服务商代开发

不加对方为开发者，而是走「微信开放平台 → 第三方平台」授权：企业把小程序授权给服务商平台，服务商通过 API 代开发代上传。权限可随时撤销，服务商拿不到账号主体信息。这是正规外包做法。

### ③ 多条产品线（同一个 owner）

同一个主体下有多个小程序 = 多个账号 = 多个 AppID，各自独立分配成员。一个人可以同时是这多个小程序的开发者，身份就是一个微信号，切项目不切身份。

如果这几个小程序要**共用一份云数据**（比如「用户端」和「骑手端」），正确做法是开**环境共享**：

- 前提：**必须同一主体**（都是你的，或都是同一家公司的）。不同主体申请会被直接拒绝。
- 路径：开发者工具 → 云控制台 → 设置 → 拓展能力 → 环境共享 → 开通 → 添加共享 → 填对方 AppID
- 关键前置：资源方必须先有 **`cloudbase_auth` 云函数**做鉴权，否则调用方 `cloud.init()` 会报「找不到对应的 FunctionName」
- 单层级授权：A 共享给 B，B **不能**再转发给 C
- 结算：费用由**共享环境的那一方**统一结算，不用各付各的

### ④ 多个小程序，但 owner 不同

**一句话：owner 不同 = 主体不同 = 两个互不认识的世界。**

账号、成员、云环境、备案、认证、发布，全部各自独立，**没有任何一处可以互相授权**。

| 东西 | 能否跨主体共用 | 说明 |
|---|---|---|
| 成员权限 | ❌ | 成员管理是账号级的。你在 A 的「开发者」权限，在 B 一文不值，要**各自单独申请** |
| 云开发环境 | ❌ | 环境共享**只支持同主体**。不同主体申请会被拒 |
| 云数据库数据 | ❌ | 跟着环境走，环境不共享就没有 |
| **代码** | ✅ | 代码本身不属于任何账号，一份代码可以喂给两个小程序 |
| APPID | ❌ | 每个项目文件只能绑一个，必须各改各的 |
| 云环境 ID | ❌ | 代码里写死的环境 ID **也必须改**（本项目在 `utils/config.js` 的 `CLOUD_ENV`） |
| 服务器域名、备案、认证、发布 | ❌ | 各自独立，各自的管理员各自操作 |

**同一份代码怎么喂给两个 owner 的小程序？**

`project.config.json` 里的 `appid` 是硬编码的，一个项目目录只能绑一个 AppID。两种做法：

1. **各留一份项目目录**（复制代码 → 改 `project.config.json` 的 `appid` → **同时改 `utils/config.js` 的 `CLOUD_ENV`**）
2. 代码只维护一份，上传时用命令行工具指定 appid（适合接了 CI 的情况）

> ⚠️ 只改 AppID 忘了改云环境 ID，是这块最经典的坑：第二个小程序会去连第一个的环境，而它**没有权限**，报出来的是「环境不存在 / 无权限」这类看不出原因的错误。

**三条实际建议**

1. **别指望「一个人管所有」。** 管理员上限是 **5 个**，而且**跨主体累加**——帮朋友挂的那个也占额度。
2. **owner 不同 = 你没有最高控制权。** 换管理员要**原管理员扫码授权**。如果某个小程序的管理员是别人，你对自己做的东西没有最终控制权，他哪天不配合，你就卡住了。
3. **要做配套小程序，就走同主体 + 环境共享。** 比如以后想加个「家属端」，正确路线是**用同一个企业主体再注册一个**小程序，而不是找个别人的账号来挂。

**决策表**

| 你的情况 | 该怎么做 |
|---|---|
| 几个小程序都是自己的 / 同一家公司的 | 各自开账号，需要共用数据就开环境共享 |
| 其中一个是别人的 / 公司的 | 让他把你加为「开发者」；**云环境各用各的**；代码可以复用，但 AppID 和环境 ID 各自改 |
| 想让两个小程序共用一份数据 | 必须同主体 + 环境共享。做不到就各存各的，别硬凑 |

## 五、企业管控的三个关键点

1. **离职处理**：从成员管理移除该员工 → 他立刻无法再用工具操作项目；代码仓库与云端资源都在企业账号下，一样不少
2. **管理员微信号必须是企业可控的人**：若管理员是离职员工或外包个人微信，后续改 AppID、开云开发、发布都会卡死，只能走繁琐的主体变更
3. **云开发有独立权限**：环境归属 AppID；如需更细粒度控制（如实习生不能改线上环境），云开发控制台有独立的权限设置项

## 六、报错与概念对照表

| 报错 / 现象 | 真实原因 | 处理 |
|---|---|---|
| 「测试号 AppId 无法使用当前功能」 | 项目还是 `touristappid` 测试号，云开发等能力需要正式身份 | 换上真实 AppID |
| 自动预览报错 `100129` | ① 云函数目录为空导致打包失败 ② 用测试号 | 补全云函数四件套；换正式 AppID |
| 图片能预览但提示"请拍一张照片" | 上传云存储失败，`fileID` 为空 | 检查云开发是否开通、环境 ID 是否填对 |
| 云开发点开没有环境列表 | 尚未开通，或 AppID 未生效 | 在 mp 后台「开发 → 云服务 → 云开发 → 开通」 |
| 工具里能改代码，但预览/上传报「无权限」 | 当前扫码的微信号不是该项目成员 | 让管理员在「成员管理」把你加为「开发者」 |
| 添加成员时提示微信号不存在 | 输入的是昵称或手机号；或对方没设置过微信号 | 让对方在微信「我 → 个人信息 → 微信号」里查看/设置 |

## 九、环境变量（云函数用，部署时在控制台配置）

| 变量名 | 说明 |
|---|---|
