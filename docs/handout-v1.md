# 衣适 · 学生讲义（第一版）

> 日期：2026-09-18
> 这份讲义只干一件事：让你知道**从明天起按什么顺序做什么**，以及**做到什么样算完成**。
> 不用先理解全部原理 —— 照着做，做完再回头看「为什么这么定」。
> 更细的验收标准在 [requirements-v1.md](requirements-v1.md)，任务清单在 [todo.md](todo.md)。
> **本讲义决定的是顺序**：AI 放最后，先做一条不依赖模型也能走完的路。

---

## 一、这个项目是干什么的

帮**动作不太方便的人**挑**好穿**的衣服 —— 不是好看的衣服。

- 只判断衣服的**结构**：怎么开合、领口袖口松不松、有没有松紧、面料弹不弹。
- 不评价款式、颜色、好不好看，也**不收集疾病信息**。
- 界面上一律说「动作不太方便」，**不出现**「残障 / 残疾 / 病人 / 疾病」这四类词。
- 分数是**「对这个人」的参考值**：同一件衣服，换一组动作难点，分数就会变。这句话必须写在界面上，不能让人以为这是衣服的绝对好坏。

---

## 二、第一版做什么、不做什么

**做：**

1. 选称呼 + 至少一项动作难点（扣扣子／拉拉链、抬手／套头、弯腰／抬腿）
2. 从**预置衣服库**里挑一件（先看推荐的那件）
3. 看到这件衣服的分数、结构发现、每条发现的**理由**、还需要向商家确认什么
4. 复制一段问商家的话术，收到货后按试穿清单自查
5. 看「更合适的结构是什么样的」，以及这件差在哪

**不做：** 商品搜索、下单、自动联系商家、多用户档案、历史衣橱、生成服装图片、医学判断。

**AI 看图放最后。** 第一版的所有结论都来自**人工录入的结构属性**，不是模型猜的。

---

## 三、为什么 AI 放最后（已有实测证据）

不是保守，是**已经试过，并且失败了**。9 月 18 日用真实模型跑了 8 次，结论都记在
[model-recon-20260918.md](model-recon-20260918.md)：

| 实测结果 | 意味着什么 |
|---|---|
| 真实商品图上，「领口纽扣难操作」的点落在**下巴**，重复请求又落在**脸**上 | **坐标不可信**。打了点反而是假精确 |
| **不给图片**，模型照样编出「圆领套头上衣」、62 分、坐标，还通过了结构校验 | 不能靠模型自觉拒答，**缺图必须由程序拦住** |
| 看不清的袖口，模型说「无束缚」「没有紧绷的松紧带」 | 它会把「看不清」说成「没问题」，这是最危险的一类错 |
| 6 次带图请求耗时 **15.3–17.3 秒**，都超过当前 15 秒预算 | 超时要改**三层**：模型请求、云函数、客户端等待 |
| 本机调 OpenAI / 百炼走的是新加坡 VPN，云函数在境内 | **本地成功 ≠ 云端能用**，这条必须实测，不能推 |

把这五条摆在一起看：**模型能识别衣服类型，但不能信任它给的位置和「没问题」的判断。**
所以第一版把识图这件事交给人 —— 衣服是预置的，结构是我们自己录的，坐标是我们自己标的。
模型等这条路跑通了再接，接的时候按第十节的四道闸来。

## 四、评委看到的那条路（journey）

```
① 穿衣需求页    选称呼 + 勾动作难点
        ↓
② 添加衣服页    「从示例衣服里选」→ 列表按推荐顺序排，第一名标「最合适」
        ↓
③ 分析结果页    预置图 + 分数 + 发现（每条带理由）+ 待确认事项
        ↓
④ 购买确认页    复制问商家的话术 + 收货后的试穿清单
        ↓
⑤ 理想款对比    这件 vs 更合适的结构，说清差在哪
```

**演示的关键动作**（这一下最能说明产品立场）：

> 回到①，把「扣扣子费劲」改成「抬手费劲」→ 同一件衣服，**分数变了、理由变了、推荐的第一名也变了**。

如果换一组难点，结果一模一样，那这个产品就没有存在的必要。**这一条是硬性验收点。**

## 五、预置衣服库：每件衣服要录什么

新建 `utils/garments.js`。每件衣服是一个对象，**属性由人录入，不是模型猜**：

```js
{
  id: 'cardigan-buttons',
  name: '针织开衫',
  image: '/assets/garments/cardigan-buttons.png',
  category: 'top',
  attrs: {
    closure:  { value: 'buttons-5',    evidence: 'visible' },  // 前开襟 · 5 颗真纽扣
    neckline: { value: 'open-front',   evidence: 'visible' },  // 前开领，不用套头
    cuff:     { value: 'regular',      evidence: 'visible' },
    stretch:  { value: null,           evidence: 'unknown' }   // 图上判断不了 → 待确认
  },
  markers: [ { x: 41, y: 16, type: 'good', ref: 'neckline' } ]  // 人工标，与 viewBox 绑定
}
```

规则：

- **图上判断不了的一律 `evidence: 'unknown'`**（面料弹性、实际尺码、是不是装饰扣）。
  这一版里 `stretch` 默认就是 `unknown` —— 图是我们画的，画不出弹性。**不许为了填满字段而猜。**
- 每件衣服都要标明「**结构示意**，不是某个在售商品」。
- 图用 SVG 手绘，`tools/build-assets.js` 出 PNG。**同一张底稿改结构细节最快** —— SVG 是文本，
  改几颗扣子、换条拉链就是另一件衣服，不用重画。
- 第一版**先做 4 件**就够演示：好一件、中一件、差一件、陷阱一件。
  （示例：5 颗纽扣开衫 / 大拉环拉链开衫 / 圆领套头衫 / 后拉链背心。
  最后那件是「陷阱款」—— 拉链在背后，自己穿不了，让评委看到系统敢说「这件不行」。）
- 首轮只做上衣、开衫。裤子外套先不碰，没验证过就不宣称支持。

## 六、规则表：动作难点 × 结构属性

新建 `utils/rules.js`。一条规则 = 「某个难点 + 某个属性值 → 省力 / 注意 / 待确认 + 一句人话」。

| 动作难点 | 看哪个属性 | 省力 | 注意 | 待确认 |
|---|---|---|---|---|
| 扣扣子／拉拉链费劲 | `closure` | 磁吸、魔术贴、大拉环拉链、无开合 | 5 颗以上真纽扣、半开襟小扣 | 分不清是真扣还是装饰扣 |
| 抬手／套头费劲 | `neckline` + `closure` | 前开襟（不用过头顶）、宽松领 | 套头 + 窄领 | 领口实际松量 |
| 弯腰／抬腿费劲 | `waist` / `length` | 松紧腰、抽绳 | 纽扣+拉链腰头、过长的下摆 | 实际尺码 |

规则写在 `utils/` 里，就能被 Node 直接测。**不要在页面里写 if-else 判断结构** —— 那样测不了。

## 七、分数怎么算（这一次是真的加权）

现在文档里写着「按动作难点加权」，但 `utils/` 和云函数里**根本没有任何权重**，
`fallback-analysis.js` 就是四个分项取算术平均。要么真做，要么改掉说法。第一版**真做**：

- 四个分项：穿脱省力 / 开合操作 / 袖口宽松 / 尺码友好
- 被选中的难点，对应分项**权重 3**；没被选中的**权重 1**
- 例：勾了「扣扣子」+「抬手」 → `(3×开合 + 3×穿脱 + 1×袖口 + 1×尺码) ÷ 8`
- **`evidence: 'unknown'` 的分项不进总分，分母也去掉**，界面显示「待确认」
- 一个分项都判不出来 → **总分不显示**，不能把未知算成 0 分

权重表写死在 `utils/score.js`，界面上要能说清「按你勾的这三项算的」。
这样「换个人分数会变」就不是一句广告词，而是算出来的。

分数**不换算成「可以买」**。建议必须指向具体结构依据。

## 八、理由怎么写（模板拼，不是模型生成）

每条发现必须能追溯到「哪条规则 × 哪个属性值」：

```
{难点}：{属性}是{属性值} → {判定}。{一句人话}
```

例：

> 扣扣子费劲：前襟是 **5 颗真纽扣** → 注意。
> 扣扣子费力的人，5 颗小纽扣是最常见的一道坎，建议先问商家能不能换拉链款。

反面例子（**不要写**）：「这件衣服整体比较友好，建议购买」 —— 没有依据，等于没说。

## 九、图片标注：预置图可以标，真实照片不标

- **预置图的坐标是人工标的**，和图源绑定，可信，可以打点。
  改 `assets/*.svg` 的 `viewBox` 必须重算所有 markers，改完跑 `node tools/verify-markers.js`。
- **⚠️ 先修一个已知 bug 再打点**：结果页 `.garment-wrap` 有 `padding: 24rpx 0`，
  标注的百分比是相对**容器**不是相对**图片**，误差 = `48×p% − 24` rpx ——
  整组点被压向画面中间。示意图上下有留白所以看不出来，换了图就会露。
  **`verify-markers.js` 抓不到这个**（它校验 SVG 源像素，不是渲染后的布局），必须真机看一眼。
- **真实照片不打点**（降级规则）：实测坐标会落到脸上。真照片只给
  **分数 + 部位名称的文字说明 + 待确认问题 + 商家话术**。
  如果最后连部位名也不可靠，就只保留有依据的文字，**不强行打点**。

一句话：**宁可少一个点，不要一个错的点。**

## 十、AI 最后怎么接（四道闸，缺一不可）

确定性版跑通之后再回来做这步。四道闸：

1. **缺图阻断**：没有图片就中止真实分析，绝不调用模型。（实测：无图也会编出合格 JSON）
2. **坐标不作为必需字段**：模型给的坐标最多留作诊断，不进主流程。
3. **超时三层一起改**：模型请求预算（实测 15–17 秒，当前 15 秒必超）、云函数执行预算、
   客户端 `wx.cloud.callFunction` 等待预算。只改一层会卡在另一层。
4. **云端可达性实测**：从腾讯云境内环境实测 DNS／TLS／鉴权／图片请求。
   **本机走 VPN 成功不算数。**

模型候选：阿里云百炼（OpenAI 兼容接口，`baseUrl` + `model` 改两个值即可）、
腾讯混元、云开发 AI+。选哪个先把候选接口在境内实测一遍再定。

## 十二、四条硬规矩

1. **优先用小程序自带组件**：`checkbox` `radio` `picker` `switch` `scroll-view` `navigator`。
   官方已经提供的**行为**（勾选状态、点击热区、滚动、表单）不要自己重做 —— 白拿点击热区和无障碍，
   对本产品的用户是实打实的体验提升。**但不要引第三方 UI 库**（Vant / TDesign），
   它们的默认配色圆角会和黑白灰规范打架。
2. **纯逻辑进 `utils/`**，页面只管渲染。写在页面里就测不了。
3. **界面不写「残障 / 残疾 / 病人 / 疾病」**，一律「动作不太方便」。
   `tests/check-skeleton.js` 的第 [7] 组会扫全部 `wxml / wxss / js / json`
   （排除 `node_modules`、`cloudfunctions`、`tests`），**写了就会挂**。
   （`docs/` 不参与扫描 —— 那里讨论产品立场，不是界面文案。）
4. **不编造数据。** 没有的就说没有 —— 判断不了写「待确认」，不要给个好看的数字。

视觉：纯白底、文字三档灰（`#1A1A1A` / `#6E6E6E` / `#A8A8A8`）、1px 分隔线 `#ECECEC`、
黑色胶囊主按钮、选中态用**描边不用填充**、8px 网格。
语义色只有两个，只用在结果页和对比页的圆点上：`#3D7A5F` 省力、`#C77D2B` 注意。其余一律黑白灰。
（本项目明确不接受「AI 味」：米色底、多色卡片、渐变、大圆角阴影。判断标准是像出版物，不像模板。）

**卡住了：** 编译报错 → 「清缓存 → 全部清除」→ 重新编译；扫码说没权限 → 回第十一节第 2 步；
其他 → 截图发给项目管理员。
