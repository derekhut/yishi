## 重大发现 1：生产封装从未成功过（已修复）

**现象**：完整提示词下发请求，60 秒 0 字节（云函数封装、`try-model.js`、甚至裸 curl 全部超时）；但极短的测试请求 3 秒就回。

**根因**：qwen3.8-max 是思考模型，默认开思考，非流式请求要等思考全部生成完才返回。第一轮侦察记录里写过诊断脚本显式传了 `reasoning_effort: none`——**那个参数没有进生产封装**。也就是说：

- 第一轮的「15–17 秒」是带 none 的诊断成绩；
- 生产链路（云函数封装）**从来没有成功返回过**，T11 一直没做反而掩盖了这一点。

**实测**：同一份完整请求体，加 `reasoning_effort: "none"` → 14.0 秒返回合格 JSON；不加 → 60 秒 0 字节。

**修复**：`lib/model.js` 的 `buildRequestBody` 支持 `reasoningEffort`（不传则不带该字段，不给不支持它的接口添乱）；云函数与 `try-model.js` 默认 `'none'`，可用环境变量 `MODEL_REASONING_EFFORT` 覆盖。守着它的测试：`tests/check-model-request.js`（6 项）。

**边界**：这个参数是百炼兼容接口的扩展，换了模型必须重新验证——写进了 `index.js` 注释和 T11 的候选项。

## 重大发现 2：坐标可靠性大幅好于第一轮

对 4 张预览图逐点人工核对，**13 个标注点全部落在衣服上**，且绝大多数对应正确部位：

- s1：两个 warn 都在门襟扣件区，good 在 V 领口和袖身 —— 全中；
- s2：拉链头（warn）、左袖口松紧（good）、下摆松紧（good）—— 全中；
- s3（竖、衣服偏小）：门襟扣子区 ✅、右袖口（贴边）✅、左袖 ✅；
- s4（斜置）：门襟上部 ✅、领口 ✅、右袖口 ✅。

第一轮「标注落到人脸/衣服外」**没有复现**。两轮差异：第一轮样本是示意图（透明背景）和带广告文字的商品图，本轮是纯色背景的真实平铺照。据此把第一轮「坐标不可靠」的结论**收窄**为：示意图与复杂背景下不可靠，纯色平铺照下可用。

**方案影响（T04）**：部位说明卡片仍是主方案，但可以加回「轻量标注」作为增强——非必需字段、允许偏移、错了不致命。是否最终保留，等补齐套头衫与模糊样本后再定。

## 发现 3：分数波动 ±10
