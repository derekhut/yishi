# 从零复现「衣适」——零基础动手手册

> 写给：完全没有开发工具、也没写过小程序的同学。
> 目标：把这套东西自己做出来，并且**能跑、能演示、能讲清楚为什么这么做**。
> 读完预计：第一次通读 20 分钟；真正动手做完约 3–5 天（每天 3 小时）。
>
> **嫌长？** 想直接抄提示词看 `prompt-for-model.md`（由脚本生成，勿手改）。
> 想要**跟本项目无关的通用教程**（装环境、账号与权限、Git 协作、排错、答辩），见
> https://github.com/derekhut/miniprogram-onboarding-guide —— 那份换个项目也能用。
> 这份文档的价值在后面那些「为什么这么设计」——动手时可以先跳过，答辩前一定要回来看。

---

## 0. 开始之前，先听三句实话

**第一句：不要"先学完再做"。**
你不需要先学完 JavaScript、WXML、云开发再看这个文档。你需要的是：每一步都能在屏幕上看到变化，卡住了再回去查那一块。这个项目一共 5 个页面，每个页面只有 1 个屏幕，学一点就能做一点。

**第二句：每一步的终点都是"能点"。**
我把整个活儿切成 5 个阶段、7 个小任务。每个任务的验收标准都是**你去点一遍界面**，而不是"我看懂了"。凡是点不出来，就是没做完。

**第三句：报错是常态，不是你没天赋。**
这个项目在开发过程中踩过至少 6 个坑（第 6 章列了）。踩坑→定位→修掉，这就是开发本身。

### 全景图

| 阶段 | 做什么 | 产出 | 需要联网账号吗 |
|---|---|---|---|
| 1 | 装环境、注册账号 | 能打开开发者工具 | 需要 |
| A | 先把成品跑起来 | 看到 5 个页面 | 不需要 |
| B | 自己重写 7 个任务 | 自己的小程序 | 不需要 |
| C | 接上真实 AI | 真分析照片 | 需要 API Key |
| D | 排练演示 | 3 分钟讲完 | 不需要 |

**特别注意阶段 A 和 C 的"不需要"。** 这套程序被特意设计成：**没有云、没有 API Key 也能完整演示**。内置了一份示例数据当保险丝。所以你先别急着申请 API Key——那是最后一步，而且很可能用不上（见第 4 章）。

## 1. 装环境、注册账号（半天，只做一次）

### 1.1 注册小程序账号

1. 打开 <https://mp.weixin.qq.com/>，点右上角「立即注册」。
2. 选「小程序」。
3. 用一个**没用过小程序平台**的邮箱注册（一个邮箱只能注册一个）。
4. 主体类型选「个人」就行。
   - 个人主体**可以用云开发**（数据库、存储、云函数都开放），够这个项目用。
   - 但如果你能通过学校／社团拿到**企业主体**，权限更宽，以后想加别的能力不用重做。
5. 注册完登录进去，左侧「开发」→「开发管理」→「开发设置」，找到 **AppID**，复制下来。形如 `wx5b899ef4f7bef91e`。

> ⚠️ 一个坑：小程序**认证**和**备案**现在都不需要做。开发版、体验版、真机预览都不受限制。只有"正式发布给所有人用"才需要。黑客松阶段完全不用管。

### 1.2 装微信开发者工具

1. 打开 <https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html>
2. 选「稳定版 Stable Build」，按你的系统下载（Windows 64 位 / macOS）。
3. 装完后打开，用**微信扫码登录**（用注册小程序时那个微信）。

### 1.3 装 Node.js

用来在电脑上跑测试脚本，不需要它也能开发小程序，但强烈建议装——它就是你的"自动检查器"。

1. 打开 <https://nodejs.org/>，下 **LTS 版本**。
2. 一路下一步装完。
3. 打开「终端」（macOS）或「命令提示符」（Windows），输入：

```bash
node -v
```

看到 `v20.x.x` 或更高的版本号就成功了。

### 1.4 验证环境

三条命令，都出结果才算过：

```bash
node -v          # 出 v20.x 或更高
git --version    # 出 git version x.x（没装 git 也可以，见下）
```

macOS 上如果 `node` 提示找不到命令，先关掉终端再重新打开一次（环境变量要重载）。

## 2. 阶段 A：先把成品跑起来（1 小时）

**为什么先做这个？** 因为你得先看到终点长什么样，才知道自己每一步在往哪走。更重要的是：**跑起来不需要任何云资源**，你现在就能看到完整界面。

### 2.1 导入项目

1. 打开微信开发者工具 →「导入项目」。
2. 目录选到 `yishi/` 这一层（注意不是它的上级，是里面有 `app.json` 的那一层）。
3. AppID 填你自己 1.1 步拿到的那个。
4. 后端服务选「不使用云服务」也可以，先看界面。

### 2.2 跑一遍测试

在终端里进到项目目录：

```bash
cd 你的路径/yishi
node tests/run-all.js
```

正常会看到 7 行「结果: N 通过, 0 失败」，最后一行 `全部套件通过 (7/7)`。

**这一步的意义**：这些断言就是这个项目的"验收标准"。它们检查的是——文件结构对不对、页面四件套齐不齐、有没有出现不该出现的词、云函数的数据格式对不对、坐标有没有跑到画面外。**全部自动检查，不需要人眼。**

> 别看总数，看每行末尾的 `0 失败`。你每加一个文件，总数就会变，写死数字只会误导自己。

### 2.3 点一遍五个页面

在开发者工具的模拟器里：

1. 选一个动作难点 → 下一步
2. 点「先用示例数据看看」
3. 看到分数、四个条形、图上三个标注 → 下一步
4. 看到问题清单 → 点「复制话术」
5. 点「看看理想款长什么样」

五步都点通，阶段 A 就完成了。**现在你知道终点在哪了。**

## 3. 阶段 B：自己重写（核心，7 个任务）

### 先说清楚：什么该复用，什么该自己写

**默认用小程序自带的组件，不要重复造轮子。** 只有内置组件确实做不到时，才自己写。

| 需求 | 用什么 | 别自己写 |
|---|---|---|
| 多选、勾选清单 | `<checkbox-group>` + `<checkbox>` + `<label>` | 别用 `<view>` + `bindtap` + CSS 画方块和对勾 |
| 单选 | `<radio-group>` + `<radio>` | 同上 |
| 开关 | `<switch>` | 别用两张图切换 |
| 下拉选择、日期时间 | `<picker>` | 别自己做弹层列表 |
| 文字输入 | `<input>` / `<textarea>` | — |
| 拖动调值 | `<slider>` | — |
| 长列表、横向滚动 | `<scroll-view>` | — |
| 轮播 | `<swiper>` | — |
| 页面跳转 | `<navigator>` | 简单跳转不用写 JS |
| 小图标（对勾等） | `<icon>` | 内置类型有限，不够用时再自己画 |
| 按钮 | `<button>` | 用它，然后改样式；别用 `<view>` 假装按钮 |

**不要引第三方 UI 库**（Vant Weapp / TDesign / uView / ColorUI）。原因不是"自己写更好"，而是：它们自带一整套颜色和圆角，会跟第 1 步定下的黑白灰规范打架，你最后要花更多时间去覆盖它的默认样式。

**那什么时候自己写？** 分界线是——**官方组件提供的是"行为"，还是"图形"**：

- **行为**（勾选状态、点击热区、滚动、表单、无障碍读屏）→ **一定用官方组件**。这些东西自己写容易漏掉细节，也测不到。
- **图形**（一根发线条、一个进度圆点、一个小加号）→ **CSS 完全合理**。画个形状不叫造轮子。
  - 例：那四根分数条用 `<progress>` 反而做不成 4rpx 的发线，自己写 20 行 CSS 更对。
  - 例：内置 `<icon>` 只有 success / info / warn / cancel 等类型，**没有加号**，所以上传区的加号必须自己画。

**还有一条容易忽略的**：项目一开始就在 `app.json` 里写了 `"style": "v2"`。这会让所有内置组件直接套用微信官方 WeUI 2.0 的外观——**这是官方设计规范，不是"默认样式"，别急着覆盖它**。

### 先讲清楚"怎么做"，再讲"做什么"

原作者（我）用的是一种叫 **TDD** 的做法，循环是：

```
写下"这一步做完应该是什么样"  →  写代码  →  跑检查  →  红了就改，绿了才下一步
```

**但你刚开始不用一步到位。** 建议这样分：

- **任务 B1–B3：先用"手点"当检查。** 每做完一个页面，就在模拟器里点一遍，把"应该能做什么"当成验收清单。
- **任务 B4 开始：升级成脚本检查。** 因为云函数没有界面，你点不出来，必须靠脚本来验。

> 为什么这个顺序？因为对零基础来说，"写测试"比"写页面"更难。先在熟悉的界面上建立"我能判断对错"的信心，再学用脚本判断。

### 每个任务的固定格式

- **目标**：一句话说清这一步要让什么能工作
- **验收**：具体点哪里、应该看到什么
- **关键文件**：要新建/改哪些文件
- **实现要点**：容易写错的地方
- **为什么这么设计**：这一步背后的判断（这是最值钱的部分，答辩会被问）

### B1 · 骨架与设计规范

**目标**：让 App 能打开，并且定下全局的颜色和字号。

**验收**
- [ ] 开发者工具打开是白底页面，标题「衣适」
- [ ] `node tests/check-skeleton.js` 全绿

**关键文件**：`app.json`、`app.wxss`、`app.js`、`project.config.json`

**实现要点**
1. `app.json` 里注册 5 个页面，顺序就是流程顺序：
   `profile`（穿衣需求）→ `add`（拍照）→ `result`（分析结果）→ `confirm`（购买确认）→ `ideal`（理想款）
2. 每个页面必须有**四件套**：`index.js` / `index.json` / `index.wxml` / `index.wxss`。少一个就编译不过。
3. 在 `app.wxss` 的 `page {}` 里定义一组全局变量，后面所有页面都用它们：

```
--ink: #1A1A1A     主文字（近黑）
--ink-2: #6E6E6E   次要文字
--ink-3: #A8A8A8   提示文字
--line: #ECECEC    1px 发线
--soft: #F7F7F7    浅底
--good: #3D7A5F    省力（绿）
--warn: #C77D2B    注意（琥珀）
```

4. 顺手写一条**文案禁词检查**：扫描所有页面文件，确保不出现「残障」「残疾」「病人」「疾病」这几个词。

**为什么这么设计**
- **为什么先定 token 再写页面？** 5 个页面如果各写各的颜色，改一次要改 5 个地方。定义一次，全局改一次。
- **为什么要禁词检查？** 这个产品是给"动作不太方便的人"用的。**用医学词汇定义用户，是把人变成标签。** 界面上一律说「动作不太方便」。这件事在产品上是尊重，在合规上是红线——所以用脚本强制执行，不靠自觉。
- **为什么是 1px 发线而不是卡片阴影？** 卡片+阴影是"AI 生成界面"最常见的味道。用一根极细的线分隔，干净得多。

### B2 · 穿衣需求页（profile）

**目标**：让用户勾选"哪些动作比较费劲"。

**验收**
- [ ] 三张卡片能点选、再点能取消，选中的外框变黑（不是填充色块）
- [ ] 一个都不选就点「下一步」，弹提示「请至少选一项」，且不跳页
- [ ] 选好点「下一步」，跳到 add 页
- [ ] `node tests/check-profile.js` 全绿

**关键文件**：`pages/profile/*`、`utils/store.js`

**实现要点**
1. 三个选项固定为 `buttons`（扣扣子）/ `liftArm`（抬手套头）/ `bend`（弯腰）。
2. **多选直接用 `<checkbox-group>` + `<label>` + `<checkbox>`**，不要手写勾选框：
   ```xml
   <checkbox-group bindchange="onChange">
     <label wx:for="{{options}}" wx:key="key" class="opt {{item.selected ? 'sel' : ''}}">
       <view class="opt-text">…</view>
       <checkbox class="opt-ck" value="{{item.key}}" checked="{{item.selected}}" color="#1A1A1A" />
     </label>
   </checkbox-group>
   ```
   - `<label>` 把整张卡片包起来，**点击热区是白拿的**
   - 勾选状态由 `checkbox-group` 管，你只需要在 `onChange` 里把 `e.detail.value`（选中项 `value` 的数组）同步回视图模型
   - 卡片外框还是自己画的（官方没提供"卡片"组件），但那个对勾不用你画
3. 把"纯逻辑"抽到 `utils/store.js`，页面只管显示：
   - `saveProfile(wx, profile)` / `loadProfile(wx)`
   - `isValidProfile(p)`：空数组算无效
   - `normalizeProfile(raw)`：去掉重复项和非法值
4. 页面只做三件事：读存储 → 渲染 → 存存储后跳转。

**为什么这么设计**
- **为什么把逻辑抽到 `utils/`？** 因为 `pages/` 里的代码依赖小程序环境，测不了。抽到 `utils/` 的纯函数可以直接 `require` 进 Node 里测。**这是整个项目能被测试的前提。**
- **为什么选中态用描边不用填充？** 填充色块是"选项卡"的语言，描边是"我选中了这一项"的语言。后者更轻，也更不像模板。

### B3 · 拍照上传页（add）

**目标**：能拍照/选图，上传到云端，拿到一个文件 ID。

**验收**
- [ ] 能调起相机或相册
- [ ] 选完出现预览图，有「换一张」
- [ ] 点「开始分析」能进结果页
- [ ] 点「先用示例数据看看」也能进结果页
- [ ] `node tests/check-add.js` 全绿

**关键文件**：`pages/add/*`、`utils/upload.js`、`utils/config.js`

**实现要点**
1. 用 `wx.chooseMedia` 选图（相机和相册都支持）。
2. 上传用 `wx.cloud.uploadFile`，云端路径加 `yishi/` 前缀避免撞名。
3. **重点：把上传失败的错误翻译成人能看懂的话。** 抽一个 `normalizeError(err)`，把原始报错映射成：
   - 云环境问题 → 「请确认云开发已开通并填入环境 ID」
   - 网络问题 → 重试提示
   - 权限问题 → 相册权限提示

**为什么这么设计（这个坑值得单独讲）**

开发时遇到过一个真机问题：**图片在界面上能预览，但点「开始分析」却提示「请拍一张照片」。**

查下来是两个问题叠加：
1. 真因：云开发没开通，上传静默失败了。
2. **但这是我的产品缺陷**：图片明明在屏幕上，界面状态却是"没拍照"，而且**错误被吞掉了**，什么都没告诉用户。

修法三条，你也要照做：
- 上传失败要有**独立的失败状态**（页面显示一行琥珀色提示）
- 错误要**记录原始信息**到控制台，方便排查
- 用户点「开始分析」时，如果发现图在但没传成功，**自动重试一次**再说，别直接拒绝

> **记住这条原则：用户看到的界面状态，必须和真实状态一致。** 图片在就得认，错误吞掉等于骗人。

### B4 · 分析云函数（analyze）—— 最难也最关键的一步

**目标**：把衣服照片 + 用户画像发给 AI，拿回一份结构化分析结果。

**验收**
- [ ] 云开发控制台里点「云端测试」，返回结果里有 `"ok": true`
- [ ] 不配任何环境变量时，返回 `"source": "fallback"`（走兜底）也**算通过**——这正是保险丝在工作
- [ ] `node tests/check-analyze.js` 全绿

**关键文件**：`cloudfunctions/analyze/` 下的 `index.js` + `lib/` 五个模块

**把这个函数拆成五个小块**（每一块都能单独测）：

| 文件 | 负责什么 |
|---|---|
| `prompt.js` | 系统提示词 + 怎么把用户画像拼进消息里 |
| `schema.js` | 检验 AI 返回的 JSON 合不合格、把脏数据洗干净 |
| `sample.js` | 内置示例数据（保险丝） |
| `model.js` | 拼 HTTP 请求、发出去、解析返回的 JSON |
| `analyze.js` | 编排：调一次 → 不合格就再调一次 → 还不行就用示例数据 |

**实现要点**

1. **让 AI 只判断结构，不判断美丑。** 系统提示词里明确：只看开合方式、领口、袖口、门襟、裤腰、松紧、材质弹性。不评价款式和颜色，不做医学判断。
2. **要 AI 返回严格的 JSON**，并给出完整字段说明。字段包括：
   - `score` 总分（0–100）
   - `dims` 四个分项（穿脱省力 / 开合操作 / 袖口宽松 / 尺码友好）
   - `findings` 结论列表（每条分「省力」或「注意」）
   - `markers` 图上标注点的坐标（百分比）
   - `questions` 要向商家问的问题
   - `script` 发给商家的话术
   - `idealFeatures` 理想款应该有哪些结构
3. **`schema.js` 要严格**：分数超出 0–100 就**判定不合格**（触发重试），不要"夹到边界"敷衍过去。字段缺失、类型不对同样判定不合格。

**为什么这么设计（这是全项目最重要的判断）**

**问题**：AI 随时可能超时、返回半截、返回一堆废话、或者返回格式不对。而你要拿这个去参加黑客松**现场演示**。

**如果演示时崩了，前面做得再漂亮都是零分。**

所以设计成四层防御：

```
第 1 层  严格校验 AI 返回的 JSON，不合格就拒收
第 2 层  拒收后自动重试一次（很多失败是偶发的）
第 3 层  两次都失败 → 用内置的示例数据，界面照常显示
第 4 层  整个函数外面再包一层 try/catch，任何意外都兜住
```

而且退到示例数据时，**必须如实告诉用户**：「当前为示例数据 · 点此重新分析」，不能假装是真的分析结果。

> 这个设计叫"保险丝"。**做演示型产品，第一优先级不是功能多，而是不会挂。**
> 另外注意：这份示例数据要按用户的难点**确定性生成**——勾了"扣扣子"开合分就是 48，勾了"抬手"穿脱分就是 92。不是随机数，这样演示时分数可复现、可解释。

### B5 · 分析结果页（result）

**目标**：把分数、结构分析、图上标注显示出来。

**验收**
- [ ] 先看到加载态（转圈 + 「通常需要 10–20 秒」）
- [ ] 看到大号分数 + 四个细线进度条
- [ ] 看到衣服示意图，上面有标注点
- [ ] 橙色数字和下面「注意」条目的编号能对上
- [ ] 云函数调用失败时，界面**照常显示**（退回示例数据），不白屏
- [ ] `node tests/check-result.js` 全绿

**关键文件**：`pages/result/*`、`utils/format.js`、`utils/fallback-analysis.js`

**实现要点**

1. 抽一层 `utils/format.js` 做"数据 → 界面"的转换：分数转百分比宽度、越界坐标夹紧、标注编号……
2. 那四个分项的条形图，就是一个灰色细条叠一个彩色细条，宽度用百分比。
   **这是"图形"，不是"行为"**——用 `<progress>` 反而做不成 4rpx 的发线，所以自己写 CSS 是对的（不是违背第 3 章的复用原则）。真正不要做的是为这四根条去装一个图表库。
3. 加载失败要 `console.error` 记下具体原因，同时退回本地示例数据。

**为什么这么设计**

- **为什么分数是"对这个人"的？** 同样一件衣服，能抬手的人打 73 分，抬不了手的人打 68 分。所以**分数旁边必须写清楚"按某某的动作难点加权得出，换一个人分数会不同"**——不然这个分数就是假精确，答辩时会被问倒。
- **真实发生过的误判**：用户勾了"扣扣子"但没勾"抬手"，看到 68 分问"我为啥是这个"。查完发现**不是 bug**，是设计如此。这件事说明：**分数必须能解释得通**，否则用户第一反应就是"你这算错了"。

### B6 · 购买确认页（confirm）

**目标**：把"不确定的事"变成可以直接发给商家的问题和话术。

**验收**
- [ ] 看到问题清单（从 01 开始编号）
- [ ] 点「复制话术」弹出「话术已复制，发给客服即可」
- [ ] 试穿清单能勾选，勾了文字变灰划掉
- [ ] `node tests/check-confirm.js` 全绿

**关键文件**：`pages/confirm/*`

**实现要点**
1. **试穿清单是标准的勾选清单，用 `<checkbox-group>` + `<label>` + `<checkbox>`**：
   ```xml
   <checkbox-group bindchange="onTryChange">
     <label wx:for="{{tryOn}}" wx:key="text" class="try-item">
       <checkbox class="try-ck" value="{{index}}" checked="{{item.checked}}" color="#1A1A1A" />
       <text class="try-text {{item.checked ? 'on' : ''}}">{{item.text}}</text>
     </label>
   </checkbox-group>
   ```
   `value` 绑下标，`onTryChange` 里用 `e.detail.value` 反查哪些被选中。
2. 「复制」用 `wx.setClipboardData`，**成功和失败都要给提示**（失败时提示「复制失败，请长按选择」）。
3. 空数据时点复制不能崩，给一句提示就行。

**为什么这么设计**
- 这一页是整个产品**唯一能立刻产生真实价值**的地方。分析得再准，用户还是不知道该怎么跟卖家说。把话说好、能一键复制，用户立刻能用上。
- **复制成功/失败都要有反馈**：不知道有没有复制成功，用户就会反复点，然后怀疑是不是坏了。
- 试穿清单**对老年人和手部不便的人尤其重要**：原生 checkbox 的点击热区比手画的大，勾错、勾不上的概率低。这里"用官方组件"不只是省事，是**真的更好用**。

### B7 · 理想款对比页（ideal）

**目标**：并排展示"现在这件"和"理想结构长什么样"。

**验收**
- [ ] 左右两栏，各有一张衣服示意图
- [ ] 左栏显示"现在这件"和分数，右栏显示"理想结构"
- [ ] 下面列出理想款应该有的结构（编号 1、2、3）
- [ ] 有一句"差距说明"
- [ ] 能复制"找款话术"
- [ ] `node tests/check-ideal.js` 全绿

**关键文件**：`pages/ideal/*`、`assets/garment-*.svg`

**实现要点**
1. 两张衣服图**手绘成 SVG**，然后用工具转成 PNG（小程序对本地 SVG 支持不稳定）。
2. 右栏**不要编造"理想款分数"**。只显示「3 处更省力」——这个数字直接由结构数量得出，是真的。

**为什么这么设计**
- **为什么右栏不编分数？** 因为我没有理想款的真实数据。编一个"理想款 95 分"看起来更漂亮，但**那是假的**。宁可少显示一个数字。
- **视觉主次怎么做？** 左栏浅灰底、不加边框；右栏白底 + 黑描边。**用边框而不是颜色来区分主次**，是这个产品贯穿始终的做法。

## 4. 阶段 C：接上真实的 AI（可选，2 小时）

### 先想清楚：你真的需要接吗？

- **不接**：程序完整可用，界面全对，只是显示的数据来自内置示例，并在界面底部如实标注「当前为示例数据」。**对黑客松演示来说，这完全可以接受，而且绝不会崩。**
- **接**：能真的分析用户拍的照片，演示效果更好，但引入了不确定性（网络、额度、超时）。

**建议：先把阶段 A/B/D 全部做完并排练好，最后才做这一步。** 因为接上之后如果出问题，你要能一键退回去。

### 4.1 选一个有"视觉能力"的模型

⚠️ **这一步最容易错**：很多便宜的模型**只能读文字，看不到照片**。你必须选**多模态/视觉**模型。

国内几个可选（都兼容 OpenAI 接口格式）：

| 服务商 | Base URL | 说明 |
|---|---|---|
| 阿里云百炼（通义千问） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 选 qwen-vl 系列。注意 API Key 和地域绑定 |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | 选 glm-4v 系列 |
| 月之暗面 Kimi | `https://api.moonshot.cn/v1` | 选带 vision 的型号 |
| 火山方舟（豆包） | `https://ark.cn-beijing.volces.com/api/v3` | 选 doubao vision 系列 |

> 具体模型名以各家控制台当前显示为准（模型名会更新）。
> 新用户通常有免费额度，但**额度会变，务必自己去控制台确认**。别在学生账号上挂信用卡。

### 4.2 建数据库集合

云开发控制台 →「数据库」→ 新建集合，名字填：

```
analyses
```

用途：把分析结果缓存 24 小时，同一张照片不重复花钱。

### 4.3 配环境变量

云开发控制台 →「云函数」→ `analyze` →「配置」→「环境变量」，加三条：

```
MODEL_BASE_URL   = 上面表里对应的 Base URL
MODEL_API_KEY    = 你的 Key
MODEL_NAME       = 你选的模型名
```

### 4.4 部署云函数

在开发者工具左侧文件树里，**右键** `cloudfunctions/analyze` 目录 →「上传并部署：云端安装依赖」。

> ⚠️ 一定要选**"云端安装依赖"**。选另一项会因为本地缺 `wx-server-sdk` 而部署失败。

### 4.5 验证

云开发控制台 → 云函数 → `analyze` →「云端测试」，随便传个参数：

```json
{ "fileID": "", "profile": { "who": "妈妈", "difficulties": ["buttons"] } }
```

看到 `"ok": true` 就是通了。如果看到 `"source": "fallback"`，说明还在走保险丝——检查环境变量有没有配全（三个缺一个都会退回兜底）。

### 4.6 一键退回保险丝

改 `utils/config.js`：

```js
FORCE_EXAMPLE: true    // 强制走示例数据
```

演示前如果发现模型不稳定，把这个改成 `true` 重新编译，立刻回到 100% 可控状态。**这是你的紧急开关，演示前务必知道它在哪。**

### 3 分钟讲什么

| 时间 | 内容 | 关键句 |
|---|---|---|
| 0:00–0:30 | 问题 | 「给行动不便的人买衣服，难的不是好看，是穿不上。」 |

## 6. 卡住了怎么办（排错表）

这些都是这个项目**真实踩过**的坑。

### 报错 `100129` / 自动预览失败

**原因一**：`cloudfunctions/` 下面有**空目录**（没有 `index.js` 和 `package.json`）导致打包失败。
→ 每个云函数目录至少要有这两个文件。

**原因二**：还在用工具自带的测试号（`touristappid`）。
→ 测试号**不支持云开发**。必须换成自己注册的真实 AppID，写进 `project.config.json`。

### 开发者工具显示「cloudfunctions（未选择环境）」

→ 点顶部工具栏的「云开发」开通，创建环境，拿到**环境 ID**（形如 `cloudbase-d5g2ft0mxecf87f08`），写进 `utils/config.js` 的 `CLOUD_ENV`。然后右键云函数目录 → 「上传并部署：云端安装依赖」。

### 部署成功但控制台「暂无云函数」

→ 正常。云函数**不会自动同步**，必须从开发者工具手动上传。

### 测试红了，说出现了「残障」这类词

→ 有人（可能就是你）在写"不要使用残障这种词"的时候，把词本身写进去了。**改成描述意图**：「不要对使用者使用任何标签化或医学化的称谓」。

### 图上标注飘到衣服外面

→ 标注坐标是**百分比**，和衣服图片的取景（SVG 的 `viewBox`）绑死。改了图片取景，坐标就得重算。
→ 这个项目做了一个像素级校验脚本，直接读图片像素看标注有没有压到衣服上：

```bash
node tools/verify-markers.js
```

**这类问题肉眼很难发现**——你会觉得"差不多在衣服上"。**别信眼睛，用脚本量。**

### 测试全绿但其实没测到东西

**真实踩过的一个坑**：汇总脚本里是**硬编码的测试清单**，新加的测试文件没登记进去，于是它根本没跑，汇总还理直气壮地显示"6/6 全绿"。

→ 修法：让汇总脚本**自动发现**测试文件（扫描目录），而不是手写清单。
→ **教训：绿色的测试如果没真的跑，比没有测试更危险。** 每加一个测试，都要确认它的名字出现在了输出里。

## 7. 不要做的事

**不要引入第三方 UI 组件库**（Vant Weapp / TDesign / uView / ColorUI）。不是"自己写更好"，而是它们自带一整套颜色和圆角，会跟第 1 步定下的黑白灰规范打架，你最后要花更多时间去覆盖它的默认样式。**小程序自带的组件当然要用** —— 见第 3 章那张对照表。

**不要用图表库画那四根进度条。** 就是个 div 加宽度百分比。这叫"杀鸡用牛刀"，跟"该用内置组件"是两回事。

**不要把内置组件重新做一遍。** 这和第 3 章那条是一回事，但值得再说一次——它是新手最容易犯的错。勾选框、单选框、开关、选择器，官方都有；用 `<view>` 加个 `bindtap` 自己拼出来，等于把"勾选"这个行为重新实现一遍，还丢了点击热区和无障碍。

**不要让 AI 判断"好不好看"。** 这个产品的立场是"好看是次要的"。让 AI 评美丑，既跑偏又没法解释。

**不要收集疾病名称。** 用「哪些动作比较费劲」代替。这是隐私，也是尊重。

**不要为了演示好看，把兜底数据伪装成真实结果。** 用示例数据就明确标注。**评委问到"这是真分析吗"，你如实说反而加分。**

**不要跳过阶段 A。** 先跑通成品再动手，能省掉大量"我到底在做什么"的迷茫。

**不要一开始就接 API Key。** 先把不需要联网的部分全做完。

## 附录 C · 给答辩准备的三个"为什么"

被问到设计决定时，这三个回答能体现你想过：

1. **为什么不收集疾病名称？**
   「因为用医学词汇定义用户，是把人变成标签。我们只关心动作能力，所以问"哪些动作费劲"就够了。」

2. **分数是怎么算的？**
   「按这个人勾选的难点加权。同一件衣服换个人分数会变，所以我们在界面上明确写了它是对这个人的参考值，不是绝对质量分。」

3. **AI 分析失败了怎么办？**
   「四层保险丝：严格校验 → 自动重试一次 → 退回内置示例数据 → 外层兜底。而且退到示例数据时会在界面底部如实标注。演示不会崩。」
